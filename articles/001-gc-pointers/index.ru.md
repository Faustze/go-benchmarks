Если в памяти сервиса живут миллионы объектов (кэш, in-memory индекс), сборщик мусора на каждой сборке обходит их: идёт от корней по указателям и в каждом живом объекте читает поля-указатели. Замер проверяет механику из кейса discord на Go 1.27.1, на синтетическом кэше без запросов и вытеснения: одни и те же 10 млн записей в четырёх раскладках. Ниже сначала что делать и как проверить свой сервис, графики в конце.

**Что значат числа.** Mark/scan по часам: сколько длится фоновая разметка, программа в это время работает. Mark CPU: сколько процессорного времени разметка съела. STW: сколько программа реально стояла, здесь не больше {{< stw >}} на сборку. Живой хип: сколько памяти занято после разметки. Остальные фазы цикла GC короткие, поэтому дальше «сборка» почти везде означает её разметку.

## Что делать

Касается только того, что живёт долго и в миллионах экземпляров. Временные объекты на запрос к моменту сборки уже мёртвые, сборщик их не обходит. Эффект ниже измерен на сборке по таймеру при 10 млн записей (mark/scan по часам).

### Ключ числом, запись значением

`map[string]*Entry` → `map[uint64]Entry`

Строковый ключ превращается в уникальный числовой id, запись хранится значением без указателей внутри. Хэш строки вместо id подходит, только если коллизии исключены или обработаны. В замере «было» соответствует LRU как у discord: такая map плюс двусвязный список. Эффект: {{< num "timer.a.green.mark_clock_ms" ms >}} → {{< num "timer.b.green.mark_clock_ms" ms >}} на сборку.

### Значение вместо указателя

`map[K]*T`, `[]*T` → `map[K]T`, `[]T`

Минус один объект и один указатель на каждую запись. Работает, если T маленький, сам без указателей и отдельная identity записи не нужна: никто не держит `*T`, запись меняется целиком через `m[k] = v`. Цена: T копируется при каждом чтении и обновлении, для большого T это дорого. Эффект: {{< num "timer.p.green.mark_clock_ms" ms >}} → {{< num "timer.b.green.mark_clock_ms" ms >}} на сборку.

### Ключ без строки

`map[string]T` → `map[uint64]T`

Строка хранит указатель на байты. Один строковый ключ заставляет сборщик обходить всю map, даже если значения плоские. Эффект: {{< num "timer.b2.green.mark_clock_ms" ms >}} → {{< num "timer.b.green.mark_clock_ms" ms >}} на сборку.

### Поля без скрытых указателей

```go
// было
CreatedAt time.Time
ID        string
Meta      any
// стало
CreatedAt int64
ID        [16]byte
Meta      Meta
```

В `time.Time` прячется `*Location`, в `string` и `any` тоже указатели. Одно такое поле делает сканируемой всю структуру. `int64` (например, Unix-наносекунды) подходит, если нужен только момент времени: часовой пояс и монотонные часы теряются. Отдельно не мерил, механизм тот же.

### Связи через индексы

`prev, next *entry` → `prev, next int32 // индексы в []entry`

Списки и деревья (LRU тоже список) можно держать в слайсе узлов. В LRU из замера `prev` и `next` дают 2 указателя из 6 на запись. Цена: освободившиеся слоты надо вести самому, например списком свободных. Отдельно не мерил.

### Строки в одном буфере

`[]string` → `buf []byte` и `span []struct{ off, n uint32 }`

Байты всех строк лежат в одном `[]byte`, запись хранит смещение и длину. Так устроены bigcache и freecache. Цена: удалённые строки оставляют дыры, буфер приходится уплотнять. Отдельно не мерил.

> **Что не помогает.** Обычные значения `GOGC` и `GOMEMLIMIT` меняют, как часто сборка приходит из-за роста кучи. Сборку по таймеру раз в две минуты они не отменяют, и каждая такая сборка обходит все живые объекты. `GOGC=off` выключает и таймер. Если при этом задан `GOMEMLIMIT`, сборки придут, когда куча дойдёт до лимита, без лимита куча растёт без сборок вообще. Это из кода рантайма и [гайда по GC](https://go.dev/doc/gc-guide), отдельно не мерил.

## Как прикинуть цену у себя

В этом замере цену разметки лучше всего объяснило число живых объектов: на i7-6700 вышло около 100 ns CPU на объект. Это цифра моего железа и моих структур (на 10 млн записей по раскладкам и режимам вышло {{< nsrange >}} ns), константой Go GC она не является. На цену влияют ещё размер сканируемой части объекта и то, как объекты разбросаны по памяти, на другом CPU цифра будет своя. Для прикидки: миллион долгоживущих объектов на i7-6700 стоит порядка 100 ms CPU на каждую сборку.

**1. Сколько объектов живёт в куче.** Метрика из стандартной библиотеки:

```go
s := []metrics.Sample{{Name: "/gc/heap/objects:objects"}}
metrics.Read(s) // import "runtime/metrics"
n := s[0].Value.Uint64()
fmt.Printf("~%v CPU на сборку\n", time.Duration(n)*100) // ~100 ns на объект
```

**2. Где их создали.** Heap-профиль по числу живых объектов, `top` покажет функции, которые создали больше всего живых объектов. Кто их удерживает, профиль не покажет, это ищется по коду:

```sh
go tool pprof -sample_index=inuse_objects http://localhost:6060/debug/pprof/heap
```

**3. Сколько длится сборка на самом деле.** Второе слагаемое в `ms clock` показывает mark/scan по часам.

**4. Пришла ли сборка по таймеру.** Перед такой сборкой gctrace печатает строку `GC forced`:

```sh
GODEBUG=gctrace=1 ./app 2>&1 | grep -A1 "GC forced"
gc 15 @128.984s 0%: 0.047+1001+0.004 ms clock, ...
```

## Где в Go прячутся указатели

Сборщик заходит внутрь объекта, если в его типе есть хоть одно поле-указатель. Тип без указателей (числа, `bool`, массивы из них, структуры из таких полей) он пропускает целиком.

| Тип | Указатели | Что внутри |
|---|---|---|
| `int, float64, bool, [16]byte` | нет | Числа и массивы чисел. Сборщик пометит объект живым и внутрь заходить не будет. |
| `struct{ ID uint64; N uint32 }` | нет | Структура из чисел тоже noscan. Именно так лежит ReadState в плоской map. |
| `string` | есть | Указатель на байты плюс длина. Ключ `map[string]T` заставляет сборщик обходить всю map: в простое она примерно в {{< ratio "timer.b2.green.mark_clock_ms" "timer.b.green.mark_clock_ms" r10 >}} раз дороже `map[uint64]T` с теми же значениями. |
| `[]T` | есть | Указатель на массив, длина и ёмкость. Слайс из чисел: один указатель на слайс, сам массив noscan. |
| `*T, map, chan, func` | есть | Каждый из них указатель. `map[K]V` сканируется, только если K или V содержат указатели. |
| `interface{}, any, error` | есть | Два слова: тип и указатель на значение. Поле `any` в структуре превращает её в сканируемую. |
| `time.Time` | есть | Внутри `loc *Location`. Структура с полем `time.Time` уже не noscan. Для кэша можно хранить Unix-время в `int64`, если не нужны часовой пояс и монотонное время. |
| struct с одним указателем | есть | Достаточно одного поля-указателя, чтобы сборщик читал весь объект и шёл по ссылке. |

## Как мерил

Два режима. **Таймер**: 10 млн записей, 11 минут простоя без аллокаций, сборки запускает только `forcegcperiod`; по три прогона на каждую конфигурацию. **`runtime.GC()`**: 8 вызовов подряд на размерах от 100 тыс. до 10 млн, один прогон на конфигурацию. Цифры из `GODEBUG=gctrace=1`, первая сборка после заливки в зачёт не идёт.

Интервал между сборками равен 120 s плюс длительность прошлой сборки: рантайм отсчитывает две минуты от её конца. У LRU без Green Tea в {{< single "timer.a.nogreen" >}} сборок размечал фактически один фоновый воркер из двух (CPU равен часам), с Green Tea всегда оба, отсюда большая часть выигрыша по часам. Это наблюдение этого замера, свойством Green Tea вообще его считать нельзя: почему без него работает один воркер, я пока не разобрал.
