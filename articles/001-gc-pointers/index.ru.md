Одни и те же 10 млн записей в памяти Go-сервиса могут стоить [сборщику мусора](#g-gc) около миллисекунды на каждую сборку, а могут почти секунду. Разница только в том, как данные хранятся: есть в их типах указатели или нет. Эта страница про то, почему так выходит и как хранить долгоживущие данные, чтобы сборщику было меньше работы. Сначала немного контекста, потом примеры, что делать и как проверить свой сервис, графики в конце. Незнакомые слова собраны в [словарике](#словарик) внизу страницы.

## Немного контекста

### Как сборщик мусора находит живые объекты

Всё, что программа создаёт через `new`, `make`, `&T{}`, срезы, строки и map, обычно живёт в [куче](#g-heap). Освобождать эту память руками в Go не нужно: время от времени запускается сборщик мусора (GC) и сам ищет, что ещё используется.

Ищет он так. Берёт [корни](#g-roots): глобальные переменные и переменные на стеках горутин. От них идёт по каждому указателю, помечает объект, до которого дошёл, как [живой](#g-live), и смотрит уже в его поля-указатели. Это называется [разметкой (mark/scan)](#g-mark). Всё, до чего сборщик не дошёл, считается мусором и освобождается.

Отсюда главное: **работа разметки растёт вместе с числом живых объектов и указателей между ними**. Если в типе нет ни одного указателя, сборщик помечает такой объект живым и внутрь не заглядывает (такие объекты называются [noscan](#g-noscan)).

Когда сборка запускается. Обычно когда куча выросла (за это отвечает [`GOGC`](#g-gogc)). Но есть ещё [сборка по таймеру](#g-timer): если сборки не было две минуты, рантайм запускает её сам. Сервис, который почти не создаёт новых объектов, получает только такие сборки.

### Что такое LRU-кэш

Кэш хранит результаты, которые дорого получать заново, например ответы базы. Память не бесконечна, поэтому у кэша есть предел, и когда он заполнен, что-то надо выкинуть. [LRU](#g-lru) (least recently used) выкидывает запись, к которой дольше всех не обращались.

Классическая реализация на Go: map от ключа к узлу плюс [двусвязный список](#g-list) узлов. При каждом обращении узел переносится в голову списка, а выкидывается узел из хвоста:

```go
type entry struct {
	key        string     // ключ, чтобы при вытеснении удалить запись из map
	value      *ReadState // сами данные
	prev, next *entry     // соседи в списке
}

cache := map[string]*entry{}
```

Удобно и быстро, но на каждую запись приходится несколько указателей: из map на узел, из узла на соседей, на данные и на байты ключа.

### Кейс discord

В 2020 году discord [переписал сервис Read States с Go на Rust](https://discord.com/blog/why-discord-is-switching-from-go-to-rust). Сервис держал в памяти LRU-кэш на миллионы записей и почти ничего не создавал заново. Поэтому сборки к нему приходили только по таймеру, раз в две минуты, и каждая обходила весь кэш. На графиках это было видно как спайк CPU и задержек ответа раз в две минуты.

Таймер в рантайме Go есть до сих пор. Я проверил ту же механику на Go 1.27.1.

## Четыре примера и зачем они такие

Во всех примерах лежат одни и те же 10 млн записей `ReadState`: два числовых поля, 16 байт, ни одного указателя.

```go
type ReadState struct {
	LastReadID   uint64
	MentionCount uint32
}
```

Меняется только способ хранения. Каждый следующий пример убирает ещё один источник указателей, чтобы было видно, сколько стоит каждый из них:

| Пример | Как хранится | Что изменилось и зачем | Указателей на запись | Объектов в куче |
|---|---|---|---|---|
| A · LRU как у discord | `map[string]*entry` + двусвязный список | Отправная точка: повторяет кейс discord | 6 | {{< num "timer.a.green.objects" count >}} |
| P · map указателей | `map[uint64]*ReadState` | Убрали список и строковый ключ, но запись всё ещё лежит по указателю. Самый частый способ хранить данные в памяти: «репозиторий» на map. Вопрос: сколько стоит один `*` на запись | 1 | {{< num "timer.p.green.objects" count >}} |
| B2 · строковый ключ | `map[string]ReadState` | Убрали `*`, запись лежит прямо в map, но ключ остался строкой. Вопрос: если в коде нет ни одной `*`, значит ли это, что указателей нет | 1, в ключе | {{< num "timer.b2.green.objects" count >}} |
| B · плоская map | `map[uint64]ReadState` | Ни одного указателя. Нижняя граница: сколько стоит сборка, когда внутрь заглядывать незачем | 0 | {{< num "timer.b.green.objects" count >}} |

Данные одинаковые специально: так разница в цене объясняется только способом хранения, а не объёмом. У B2 объектов вдвое меньше, чем ключей: байты двух коротких строк рантайм кладёт в один блок, это делает [tiny allocator](#g-tiny). P и B ещё и весят почти одинаково ({{< num "timer.p.green.live_mb" n0 >}} и {{< num "timer.b.green.live_mb" n0 >}} MB), поэтому на них хорошо видно, что сборщик платит не за мегабайты.

Условия: [синтетический](#g-synthetic) кэш без запросов и без [вытеснения](#g-eviction), заполняется один раз, дальше программа 11 минут ничего не делает, и в зачёт идут только сборки по таймеру. i7-6700, Linux, [`GOMAXPROCS=8`](#g-gomaxprocs), по три прогона на пример.

{{< kpis >}}

**Что значат числа.** [Mark/scan по часам](#g-clock): сколько длится фоновая разметка, программа в это время продолжает работать. Mark CPU: сколько процессорного времени разметка съела в сумме на всех ядрах. [STW](#g-stw): сколько программа реально стояла, здесь не больше {{< stw >}} на сборку. Живой хип: сколько памяти занято после разметки. Остальные фазы сборки короткие, поэтому дальше «сборка» почти везде означает её разметку.

## Что делать

Касается только данных, которые живут долго и в миллионах экземпляров: кэши, [in-memory индексы](#g-index), справочники. Временные объекты, созданные на один запрос, к моменту сборки уже мёртвые, сборщик их не обходит. Эффект ниже измерен на сборке по таймеру при 10 млн записей ([медиана](#g-median) mark/scan по часам).

### Ключ числом, запись значением

`map[string]*Entry` → `map[uint64]Entry`

Строковый ключ превращается в уникальный числовой id, запись хранится значением без указателей внутри. [Хэш](#g-hash) строки вместо id подходит, только если [коллизии](#g-collision) исключены или обработаны. В замере «было» соответствует LRU как у discord: такая map плюс двусвязный список. Эффект: {{< num "timer.a.green.mark_clock_ms" ms >}} → {{< num "timer.b.green.mark_clock_ms" ms >}} на сборку.

### Значение вместо указателя

`map[K]*T`, `[]*T` → `map[K]T`, `[]T`

Минус один объект и один указатель на каждую запись. Работает, если T маленький, сам без указателей и записи не нужна отдельная [identity](#g-identity): никто не держит `*T`, запись меняется целиком через `m[k] = v`. Цена: T копируется при каждом чтении и обновлении, для большого T это дорого. Эффект: {{< num "timer.p.green.mark_clock_ms" ms >}} → {{< num "timer.b.green.mark_clock_ms" ms >}} на сборку.

### Ключ без строки

`map[string]T` → `map[uint64]T`

Строка хранит указатель на свои байты. Одного строкового ключа хватает, чтобы сборщик обходил всю map, даже если значения без указателей. Эффект: {{< num "timer.b2.green.mark_clock_ms" ms >}} → {{< num "timer.b.green.mark_clock_ms" ms >}} на сборку.

### Поля без скрытых указателей

```go
// было
CreatedAt time.Time
ID        string
Meta      any
// стало
CreatedAt int64
ID        [16]byte
Meta      Meta
```

В `time.Time` прячется `*Location`, в `string` и `any` тоже указатели. Одно такое поле делает сканируемой всю структуру. `int64` ([Unix-время](#g-unix) в наносекундах) подходит, если нужен только момент времени: часовой пояс и [монотонные часы](#g-mono) теряются. Отдельно не мерил, механизм тот же.

### Связи через индексы

`prev, next *entry` → `prev, next int32 // индексы в []entry`

Списки и деревья (LRU тоже список) можно держать в одном слайсе узлов, а вместо указателей на соседей хранить их номера в этом слайсе. В LRU из замера `prev` и `next` дают 2 указателя из 6 на запись. Цена: освободившиеся слоты надо вести самому, например [списком свободных](#g-freelist). Отдельно не мерил.

### Строки в одном буфере

`[]string` → `buf []byte` и `span []struct{ off, n uint32 }`

Байты всех строк лежат в одном `[]byte`, запись хранит смещение и длину. Так устроены [bigcache и freecache](#g-bigcache). Цена: удалённые строки оставляют дыры, буфер приходится уплотнять. Отдельно не мерил.

> **Что не помогает.** Обычные значения [`GOGC` и `GOMEMLIMIT`](#g-gogc) меняют, как часто сборка приходит из-за роста кучи. Сборку по таймеру раз в две минуты они не отменяют, и каждая такая сборка обходит все живые объекты. `GOGC=off` выключает и таймер. Если при этом задан `GOMEMLIMIT`, сборки придут, когда куча дойдёт до лимита, без лимита куча растёт без сборок вообще. Это из кода рантайма и [гайда по GC](https://go.dev/doc/gc-guide), отдельно не мерил.

## Как прикинуть цену у себя

В этом замере цену разметки лучше всего объяснило число живых объектов: на i7-6700 вышло около 100 ns CPU на объект. Это цифра моего железа и моих структур (на 10 млн записей по примерам и режимам вышло {{< nsrange >}} ns), константой Go она не является. На цену влияют ещё размер сканируемой части объекта и то, как объекты разбросаны по памяти, на другом CPU цифра будет своя. Для прикидки: миллион долгоживущих объектов на i7-6700 стоит порядка 100 ms CPU на каждую сборку.

**1. Сколько объектов живёт в куче.** Метрика из стандартной библиотеки [`runtime/metrics`](#g-metrics):

```go
s := []metrics.Sample{{Name: "/gc/heap/objects:objects"}}
metrics.Read(s) // import "runtime/metrics"
n := s[0].Value.Uint64()
fmt.Printf("~%v CPU на сборку\n", time.Duration(n)*100) // ~100 ns на объект
```

**2. Где их создали.** [Heap-профиль](#g-pprof) по числу живых объектов, `top` покажет функции, которые создали больше всего живых объектов. Кто их удерживает, профиль не покажет, это ищется по коду:

```sh
go tool pprof -sample_index=inuse_objects http://localhost:6060/debug/pprof/heap
```

**3. Сколько длится сборка на самом деле.** Запусти сервис с [`GODEBUG=gctrace=1`](#g-gctrace): рантайм будет печатать строку на каждую сборку. Второе слагаемое в `ms clock` показывает mark/scan по часам.

**4. Пришла ли сборка по таймеру.** Перед такой сборкой gctrace печатает строку `GC forced`:

```sh
GODEBUG=gctrace=1 ./app 2>&1 | grep -A1 "GC forced"
gc 15 @128.984s 0%: 0.047+1001+0.004 ms clock, ...
```

## Кейс discord: сборка раз в две минуты

Программа заливает кэш и 11 минут не делает ничего. Сборки всё равно приходят раз в две минуты, и LRU каждый раз занимает два логических CPU из восьми примерно на секунду: на разметку рантайм выделяет [фоновые воркеры](#g-workers) на 25% от `GOMAXPROCS`. Под нагрузкой эта секунда делила бы CPU с запросами, а горутины, которые в это время создают объекты, могли бы попасть под [mark assist](#g-assist) и помогать с разметкой сами.

## Где в Go прячутся указатели

Сборщик заходит внутрь объекта, если в его типе есть хоть одно поле-указатель. Тип без указателей (числа, `bool`, массивы из них, структуры из таких полей) он пропускает целиком.

| Тип | Указатели | Что внутри |
|---|---|---|
| `int, float64, bool, [16]byte` | нет | Числа и массивы чисел. Сборщик пометит объект живым и внутрь заходить не будет. |
| `struct{ ID uint64; N uint32 }` | нет | Структура из чисел тоже noscan. Именно так лежит ReadState в плоской map. |
| `string` | есть | Указатель на байты плюс длина. Ключ `map[string]T` заставляет сборщик обходить всю map: в простое она примерно в {{< ratio "timer.b2.green.mark_clock_ms" "timer.b.green.mark_clock_ms" r10 >}} раз дороже `map[uint64]T` с теми же значениями. |
| `[]T` | есть | Указатель на массив, длина и ёмкость. Слайс из чисел: один указатель на слайс, сам массив noscan. |
| `*T, map, chan, func` | есть | Каждый из них указатель. `map[K]V` сканируется, только если K или V содержат указатели. |
| `interface{}, any, error` | есть | Два слова: тип и указатель на значение. Поле `any` в структуре превращает её в сканируемую. |
| `time.Time` | есть | Внутри `loc *Location`. Структура с полем `time.Time` уже не noscan. Для кэша можно хранить Unix-время в `int64`, если не нужны часовой пояс и монотонное время. |
| struct с одним указателем | есть | Достаточно одного поля-указателя, чтобы сборщик читал весь объект и шёл по ссылке. |

## Как мерил

Два режима. **Таймер**: 10 млн записей, 11 минут простоя без аллокаций, сборки запускает только таймер рантайма (`forcegcperiod`); по три прогона на каждый пример. **`runtime.GC()`**: 8 вызовов подряд на размерах от 100 тыс. до 10 млн, один прогон на конфигурацию. Цифры из `GODEBUG=gctrace=1`, первая сборка после заливки в зачёт не идёт. Всё на сборщике по умолчанию в Go 1.27.1, его же получает любой `go build`.

Интервал между сборками равен 120 s плюс длительность прошлой сборки: рантайм отсчитывает две минуты от её конца.

## Словарик

- <a id="g-gc"></a>**Сборщик мусора (GC, garbage collector).** Часть рантайма Go, которая сама находит и освобождает память, которой программа больше не пользуется.
- <a id="g-heap"></a>**Куча, хип (heap).** Область памяти для объектов, которые живут дольше одного вызова функции. Ею и занимается сборщик. Переменные, которые компилятор смог оставить на стеке, сборщика не нагружают.
- <a id="g-roots"></a>**Корни.** С чего сборщик начинает обход: глобальные переменные и переменные на стеках горутин.
- <a id="g-live"></a>**Живой объект.** Объект, до которого можно дойти от корней по указателям. Его освобождать нельзя.
- <a id="g-mark"></a>**Разметка (mark/scan).** Главная фаза сборки: сборщик обходит живые объекты по указателям, помечает их (mark) и читает их поля-указатели (scan).
- <a id="g-noscan"></a>**noscan.** Объект, в типе которого нет указателей. Сборщик помечает его живым, но внутрь не заглядывает, поэтому такой объект почти ничего не стоит.
- <a id="g-stw"></a>**STW (stop the world).** Короткие паузы в начале и конце сборки, когда все горутины остановлены. Сама разметка идёт параллельно с программой.
- <a id="g-clock"></a>**По часам и CPU.** «По часам» (wall-clock): сколько прошло реального времени. CPU: сколько процессорного времени потрачено на всех ядрах вместе. Два ядра за секунду по часам дают две секунды CPU.
- <a id="g-workers"></a>**Фоновые воркеры GC.** Потоки, которые ведут разметку, пока программа работает. Рантайм отдаёт им 25% от `GOMAXPROCS`: при 8 это два логических CPU.
- <a id="g-assist"></a>**Mark assist.** Если во время разметки горутина активно создаёт объекты, рантайм заставляет её саму поработать на разметку. Для запроса это выглядит как лишняя задержка.
- <a id="g-gomaxprocs"></a>**GOMAXPROCS.** Сколько логических CPU Go-программа может занимать одновременно. По умолчанию равно числу логических CPU машины.
- <a id="g-timer"></a>**Сборка по таймеру (`forcegcperiod`).** Если сборки не было две минуты, рантайм запускает её сам, даже если память не растёт. В gctrace перед ней стоит строка `GC forced`.
- <a id="g-lru"></a>**LRU-кэш (least recently used).** Кэш с ограниченным размером: при переполнении выкидывает запись, к которой дольше всех не обращались.
- <a id="g-list"></a>**Двусвязный список.** Цепочка узлов, где каждый хранит указатели на предыдущий и следующий. Узел можно вынуть или переставить за константное время, поэтому LRU держит на нём порядок обращений.
- <a id="g-eviction"></a>**Вытеснение (eviction).** Удаление записи из кэша, когда он заполнен.
- <a id="g-index"></a>**In-memory индекс.** Структура в памяти сервиса, по которой быстро ищутся данные: например, map от id пользователя к его настройкам, чтобы не ходить в базу.
- <a id="g-workload"></a>**Workload.** Конкретная нагрузка: какие данные, сколько и что с ними делают. Вывод, сделанный на одном workload, на другом может не подтвердиться.
- <a id="g-synthetic"></a>**Синтетический замер.** Программа, написанная только для замера. Она повторяет нужную механику, но не настоящий сервис с его запросами.
- <a id="g-tiny"></a>**Tiny allocator.** Механизм рантайма, который складывает несколько очень маленьких объектов без указателей в один 16-байтный блок. Поэтому у примера B2 объектов вдвое меньше, чем ключей: байты двух коротких строк лежат в одном блоке.
- <a id="g-hash"></a>**Хэш.** Число, которое функция вычисляет из строки. Одинаковые строки всегда дают одинаковый хэш.
- <a id="g-collision"></a>**Коллизия.** Две разные строки дали одинаковый хэш. Если ключ map это хэш, при коллизии одна запись тихо перезапишет другую.
- <a id="g-identity"></a>**Identity записи.** Когда важно, что это тот же самый объект в памяти, а не его копия: например, кто-то держит `*T` и ждёт, что увидит изменения. Если запись хранится значением, такой ссылки нет, есть только копии.
- <a id="g-unix"></a>**Unix-время.** Время как одно число: сколько секунд (или наносекунд) прошло с 1 января 1970 года по UTC. В Go: `t.UnixNano()` и обратно `time.Unix(0, n)`.
- <a id="g-mono"></a>**Монотонные часы.** Показание часов, которое только растёт, даже если системное время перевели. `time.Now()` хранит его внутри `time.Time`, чтобы `time.Since` считал длительность правильно. В `int64` оно не сохраняется.
- <a id="g-freelist"></a>**Список свободных (free list).** Список номеров освободившихся ячеек слайса, чтобы новые записи занимали их, а не растили слайс.
- <a id="g-bigcache"></a>**bigcache и freecache.** Популярные Go-библиотеки кэша, сделанные так, чтобы не нагружать сборщик: записи лежат в больших байтовых буферах, а не в миллионах отдельных объектов.
- <a id="g-gogc"></a>**GOGC и GOMEMLIMIT.** Настройки сборщика. `GOGC` (по умолчанию 100): насколько процентов может вырасти куча до следующей сборки. `GOMEMLIMIT`: мягкий потолок памяти, у которого сборщик начинает работать чаще.
- <a id="g-gctrace"></a>**gctrace.** Отладочный вывод рантайма, включается через `GODEBUG=gctrace=1`: по строке на каждую сборку с её длительностью, CPU и размером кучи.
- <a id="g-pprof"></a>**pprof и heap-профиль.** Встроенный в Go профилировщик. Heap-профиль показывает, какие функции создали объекты, которые сейчас живут в куче.
- <a id="g-metrics"></a>**runtime/metrics.** Пакет стандартной библиотеки, который отдаёт метрики рантайма: число объектов в куче, её размер, число сборок и другое.
- <a id="g-median"></a>**Медиана.** Значение посередине, если отсортировать все замеры. В отличие от среднего, один выброс её почти не сдвигает.
- <a id="g-log"></a>**Логарифмическая шкала.** Каждое деление шкалы больше предыдущего в 10 раз. Нужна, когда на одном графике числа отличаются в сотни раз.
