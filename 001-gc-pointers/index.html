Сколько стоит указатель

Если в памяти сервиса живут миллионы объектов (кэш, in-memory индекс), сборщик мусора на каждой сборке обходит их: идёт от корней по указателям и в каждом живом объекте читает поля-указатели. Замер проверяет механику из кейса discord на Go 1.27.1, на синтетическом кэше без запросов и вытеснения: одни и те же 10 млн записей в четырёх раскладках. Ниже сначала что делать и как проверить свой сервис, графики в конце.

Что значат числа. Mark/scan по часам: сколько длится фоновая разметка, программа в это время работает. Mark CPU: сколько процессорного времени разметка съела. STW: сколько программа реально стояла, здесь меньше 0,1 ms на сборку. Живой хип: сколько памяти занято после разметки. Остальные фазы цикла GC короткие, поэтому дальше «сборка» почти везде означает её разметку.

Что делать

Касается только того, что живёт долго и в миллионах экземпляров. Временные объекты на запрос к моменту сборки уже мёртвые, сборщик их не обходит. Эффект ниже измерен на сборке по таймеру при 10 млн записей (mark/scan по часам).

Что не помогает. Обычные значения GOGC и GOMEMLIMIT меняют, как часто сборка приходит из-за роста кучи. Сборку по таймеру раз в две минуты они не отменяют, и каждая такая сборка обходит все живые объекты. GOGC=off выключает и таймер. Если при этом задан GOMEMLIMIT, сборки придут, когда куча дойдёт до лимита, без лимита куча растёт без сборок вообще. Это из кода рантайма и гайда по GC, отдельно не мерил.

Как прикинуть цену у себя

В этом замере цену разметки лучше всего объяснило число живых объектов: на i7-6700 вышло около 100 ns CPU на объект. Это цифра моего железа и моих структур (на 10 млн записей по раскладкам и режимам вышло от 40 до 200 ns), константой Go GC она не является. На цену влияют ещё размер сканируемой части объекта и то, как объекты разбросаны по памяти, на другом CPU цифра будет своя. Для прикидки: миллион долгоживущих объектов на i7-6700 стоит порядка 100 ms CPU на каждую сборку.

1. Сколько объектов живёт в куче. Метрика из стандартной библиотеки:

s := []metrics.Sample{{Name: "/gc/heap/objects:objects"}}
metrics.Read(s) // import "runtime/metrics"
n := s[0].Value.Uint64()
fmt.Printf("~%v CPU на сборку\n", time.Duration(n)*100) // ~100 ns на объект

2. Где их создали. Heap-профиль по числу живых объектов, top покажет функции, которые создали больше всего живых объектов. Кто их удерживает, профиль не покажет, это ищется по коду:

go tool pprof -sample_index=inuse_objects http://localhost:6060/debug/pprof/heap

3. Сколько длится сборка на самом деле. Второе слагаемое в ms clock показывает mark/scan по часам.

4. Пришла ли сборка по таймеру. Перед такой сборкой gctrace печатает строку GC forced:

GODEBUG=gctrace=1 ./app 2>&1 | grep -A1 "GC forced"
gc 15 @128.984s 0%: 0.047+1001+0.004 ms clock, ...

Одна сборка, четыре раскладки

Медиана mark/scan по часам для сборок по таймеру в полном простое. Данные одинаковые, меняется только число указателей на запись. В скобках разброс по 12 сборкам. Шкала логарифмическая, на линейной плоская map не видна вовсе.

Цену объясняет число объектов

20 прогонов с runtime.GC() от 100 тыс. до 10 млн записей, по одному на точку, так что это наблюдение на одном workload, закон отсюда не вывести. По объёму памяти точки разбросаны на три порядка: плоская map на 426 MB стоит миллисекунду, map указателей на 441 MB стоит сотни. По числу объектов все варианты ложатся близко к одной линии.

Кейс discord: сборка раз в две минуты

Программа заливает кэш и 11 минут не делает ничего. Сборки всё равно приходят раз в две минуты, и LRU каждый раз занимает два логических CPU из восьми примерно на секунду. Полые точки: без Green Tea.

Green Tea ускорил, разрыв остался

С Go 1.26 новый сборщик включён по умолчанию. В этом замере сборку LRU он ускорил в 2,7 раза по часам, плоская map всё равно дешевле в сотни раз. Точка: медиана, линия: от минимума до максимума.

Где в Go прячутся указатели

Сборщик заходит внутрь объекта, если в его типе есть хоть одно поле-указатель. Тип без указателей (числа, bool, массивы из них, структуры из таких полей) он пропускает целиком.

Как мерил

Два режима. Таймер: 10 млн записей, 11 минут простоя без аллокаций, сборки запускает только forcegcperiod; по три прогона на каждую конфигурацию. runtime.GC(): 8 вызовов подряд на размерах от 100 тыс. до 10 млн, один прогон на конфигурацию. Цифры из GODEBUG=gctrace=1, первая сборка после заливки в зачёт не идёт.

Интервал между сборками равен 120 s плюс длительность прошлой сборки: рантайм отсчитывает две минуты от её конца. У LRU без Green Tea в 14 сборках из 15 размечал фактически один фоновый воркер из двух (CPU равен часам), с Green Tea всегда оба, отсюда большая часть выигрыша по часам. Это наблюдение этого замера, свойством Green Tea вообще его считать нельзя: почему без него работает один воркер, я пока не разобрал.

Рост с размером кэша

Вызовы runtime.GC(), CPU разметки, один прогон на точку. У вариантов с указателями цена растёт вместе с числом записей, у плоской map почти не меняется.
